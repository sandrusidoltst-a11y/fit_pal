## Feature Description

When the LLM estimates macros for an off-menu food item and the user confirms it, create a `FoodItem` row in the database with `source="estimated"`. This enables proper FK relationships in `daily_logs`, fallback search for previously estimated foods, and back-calculated per-100g values for future reuse.

## User Story

As a FitPal user
I want my confirmed estimated foods to be saved in the food database
So that I don't need to re-estimate the same food every time, and my daily logs have proper data integrity

## Problem Statement

Currently, estimated food items are logged to `daily_logs` with `food_id=NULL`. This breaks joins, loses the food name (only preserved in `original_text` free text), and prevents reuse of past estimations. Stats queries that join `daily_logs → food_items` silently drop estimated entries.

## Solution Statement

1. Add a `source` column to `FoodItem` (`"database"` | `"estimated"`, NOT NULL, default `"database"`)
2. At commit time, create a new `FoodItem` row for estimated items with back-calculated per-100g values
3. Update `search_food` to query DB foods first, then fall back to estimated foods
4. Update `SearchResult` TypedDict to include a `source` field for transparency

### Patterns to Follow

**Tool-First Architecture**: All DB access through async `@tool` functions. The new `create_food_item` tool owns its own session. `commit_node` calls it via `await create_food_item.ainvoke(...)`.

**Session Pattern** (from `search_food` in `food_lookup.py`):
```python
async with get_async_db_session() as session:
    # query / insert
```

**Tool Signature Pattern** (from `calculate_food_macros`):
```python
@tool
async def create_food_item(name: str, calories_per_100g: float, ...) -> dict:
    """Docstring for LLM."""
    async with get_async_db_session() as session:
        ...
        return {"id": food_item.id, "name": food_item.name}
```

**Migration Pattern** (from baseline migration):
```python
with op.batch_alter_table('food_items') as batch_op:
    batch_op.add_column(sa.Column('source', sa.String(), nullable=False, server_default='database'))
```

**Back-Calculation Formula**: `per_100g = round((value / amount_g) * 100, 2)` — matches `ingest_simple_db.py` lines 79-84.

## NOTES

### Design Decisions

1. **FoodItem created at commit time** (not at estimation time) — avoids orphaned rows when user rejects
2. **Single search_food tool with internal fallback** — simpler API, node doesn't need to know about search tiers
3. **Back-calculation to per-100g** — consistent with existing DB foods, enables recalculation for different amounts
4. **source column NOT NULL with default** — strict, prevents ambiguous rows
5. **Food name stored as-is** — already cleaned by LLM structured output in input parser
6. **ETL relies on column default** — no script changes needed
7. **Estimated foods still go through HITL confirmation** — consistent UX, no special cases

- `user_id` on FoodItem (Phase 3 — auth system)
- Deduplication of estimated foods (same name, different estimations)
- Updating estimated food macros over time (user corrections)
